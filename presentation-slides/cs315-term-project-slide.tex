\begin{frame}{The Problem}
    \begin{itemize}
        \item Software mixes high-security data (passwords, private keys, etc.) with low-security data. This may lead to data leaks.
        \item A develop might accidentally print a password to a debug log.
        \item An attacker might try to infer secrets by observing public behavior.
    \end{itemize}
    \textbf{The goal}:
    \begin{itemize}
        \item Ensure \emph{confidentiality}.
        \item \emph{Noninterference}: changing a secret input should have \emph{no observable effect} on public output.
    \end{itemize}
\end{frame}

\begin{frame}{What is Informational Flow Control?}
    Instead of just checking access (Can we read this file?), we check \emph{flow} (Where does this data go?).
    
    \emph{Static analysis}: we want to catch these leaks at compile time.
    
    We label data as either:
    \begin{itemize}
        \item \texttt{Pub} (Public/Low Security)
        \item \texttt{Sec} (Secret/High Security)
    \end{itemize}
\end{frame}

\begin{frame}{Core Idea: The "Security Box"}
    We use a concept called \emph{graded modality}. Fundamentally, a modality is a box with a security label:
    \begin{itemize}
        \item We can seal both public and secret data into a secret-labelled box, but we can only open it under a high-security (secret) context.
        \item We can only seal public data into a public-labelled box, but we can open it regardless of the context.
    \end{itemize}
\end{frame}

\begin{frame}{How The Type System Works?}
    We use a \emph{semiring} (A mathematical structure) to decide how security labels interact with each other:
    \begin{itemize}
        \item Order: $\texttt{Pub}\le\texttt{Sec}$
        \item Addition as meet: $r+s=r\sqcap s$
        \item Multiplication as join: $r\cdot s=r\sqcup s$
        \item $0=\texttt{Sec}$, $1=\texttt{Pub}$
    \end{itemize}

\end{frame}

\begin{frame}{Implementation}
    How we built it:
    \begin{itemize}
        \item Language: Java 17.
        \item Lexer \& Parser: Generated by ANTLR4.
        \item Type Checker: The core of the interpreter. Based on the bidirectional typing system to enforce the security rules.
        \item We also built an language server to provide basic semantic highlighting and hover hints.
    \end{itemize}
\end{frame}

\begin{frame}{Limitations \& Future Work}
    \textbf{Current status}:
    \begin{itemize}
        \item We verify the system's capability through both formal proofs and implementation.
        \item \textbf{Limitations}:
        \begin{itemize}
            \item It's a small academic language and lacks real-world programming constructs (no complex data structures, polymorphism, etc.)
            \item The effectiveness of the system has not been verified at larger scale.
        \end{itemize}
    \end{itemize}
    \textbf{Future work}:
    \begin{itemize}
        \item Extend the type system with more advanced features, e.g., \emph{parametric polymorphism}, \emph{subtyping}, \emph{dependent typing}, other form of \emph{effect/coeffect analysis}.
        \item Integrate our system into industrial languages/real-world code bases to evaluate its effectiveness.
    \end{itemize}
\end{frame}
